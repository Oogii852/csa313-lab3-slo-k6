# F.CSA313 — Лаборатори №3: Чанарын сценарио → SLO → k6 threshold

**Оюутан:** Б. Отгонсүх
**Код:** B242270021

**k6 version:** k6 v2.3.0 (commit/e088784614, go1.26.8, linux/amd64)

## Тестлэх API

Node.js + Express, гурван endpoint:
- `POST /cart/add` — хурдан endpoint (сагсанд нэмэх)
- `GET /report` — удаан endpoint (200-400мс санамсаргүй хүлээлт)
- `POST /pay` — найдваргүй endpoint (хүсэлтийн ~5% нь 500 алдаа)

## Чанарын сценариоуд (6 хэсэгтэй формат)

### Сценарио 1: Performance — /cart/add хариу хугацаа

| Хэсэг | Тайлбар |
|---|---|
| Тойм | /cart/add endpoint-ийн хариу хугацааг хэвийн ачааллын үед хэмжинэ |
| Системийн төлөв | Сервер хэвийн ажиллагаатай, унаагүй |
| Орчны төлөв | Хэвийн ачаалал: 20 VU (виртуал хэрэглэгч), тогтмол ачаалал |
| Гадаад өдөөлт | 20 хэрэглэгч нэгэн зэрэг /cart/add рүү POST хүсэлт байнга илгээнэ |
| Шаардлагатай хариу | Сервер `{ ok: true, items: 1 }` гэсэн JSON хариу буцаана |
| Хэмжүүр | Хариу хугацааны p95 < 200 мс (1 минутын турш) |

### Сценарио 2: Reliability — /pay эвдрэлийн давтамж

| Хэсэг | Тайлбар |
|---|---|
| Тойм | /pay endpoint дээрх төлбөрийн хүсэлтийн бүтэлгүйтлийн давтамжийг хэмжинэ |
| Системийн төлөв | Сервер хэвийн ажиллагаатай |
| Орчны төлөв | Хэвийн ачаалал: 20 VU, 1 минутын турш |
| Гадаад өдөөлт | Хэрэглэгч төлбөр хийх зорилгоор /pay рүү POST хүсэлт илгээнэ |
| Шаардлагатай хариу | Ихэнх тохиолдолд (≥92%) амжилттай (200), заримдаа gateway timeout (500) |
| Хэмжүүр | POFOD / error rate < 8% |

### Сценарио 3: Availability — сервер унаж дахин асахад

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Сервер гэнэт зогсоод дахин асахад системийн ерөнхий боломжит байдлыг хэмжинэ |
| Системийн төлөв | Ажиллаж байгаад гэнэт эвдэрч (crash), дараа нь дахин асна |
| Орчны төлөв | 10 VU, 2 минутын турш, дунд нь ойролцоогоор 10 секунд сервер зогсоно |
| Гадаад өдөөлт | Сервер process гараар зогсоож (Ctrl+C), 10 секундийн дараа дахин асаана |
| Шаардлагатай хариу | Систем аль болох хурдан сэргэж, зогсолтоос гадуур хүсэлтүүд амжилттай хариу авна |
| Хэмжүүр | Availability (амжилттай хүсэлтийн хувь) ≥ 90%, сэргэх хугацаа (recovery time) ойролцоогоор 10 секунд |

## SLO (Service Level Objective)

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 200 мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, 10с зогсолт орсон |

**Босго сонгосон үндэслэл:** /pay endpoint дээр серверт зориудаар ~5% алдаа суулгасан тул 8% гэдэг нь энгийн хэлбэлзлийг тэвчих боловч бодит асуудлыг илрүүлэх боломжтой, бодит дээр суурилсан босго юм. Performance-ийн хувьд 200мс нь хэрэглэгчийн хувьд "хурдан" гэж мэдрэгдэх ерөнхий стандарт хугацаа.

**Error budget тооцоо (цагаар):** Availability SLO маань 2 минутын цонхонд ≥90% байхыг шаардаж байгаа тул зөвшөөрөгдөх "эвдрэх хугацаа" нь: 120 сек × (1 − 0.90) = **12 секунд**. Өөрөөр хэлбэл, 2 минутын турш нийт 12 секундээс илүүгүй хугацаанд систем боломжгүй байж болно гэсэн үг.

## k6 Threshold-ууд (slo-test.js)

| Threshold | Тайлбар |
|---|---|
| `http_req_duration{name:cart}`: p(95)<200 | Performance SLO |
| `http_req_failed{name:pay}`: rate<0.08 | Reliability SLO |
| `checks`: rate>0.90 | Availability SLO |
| `http_req_duration{name:report}`: p(95)<450 | Нэмэлт (4-р) сценарио — /report-ийн латенси |

PASS гаралт: `results/pass.txt` (бүх 4 threshold ✓)

**Ажиглалт:** localhost дээр /cart/add ердөө ~1.14ms-д хариулдаг тул p(95)<200 threshold бодит дээр маш сул (бараг юу ч шүүхгүй) байна. Харин /report-ийн хувьд 200-400мс хиймэл хүлээлт кодонд шууд суулгасан тул p(95)<450 threshold бодит утгатай ойрхон, утга учиртай хэмжүүр болж байна.

## Chaos туршилт (Availability сценарио)

Нөхцөл: 10 VU, 2 минут (k6 run --vus 10 --duration 2m slo-test.js). Тест эхэлснээс 40 секундийн дараа сервер зогсоож, 10 секундийн дараа дахин асаасан (results/chaos-events.txt). Гаралт: results/chaos.txt, k6 exit code 99.

Threshold-ийн үр дүн (results/chaos.txt):

```
    checks
    ✗ 'rate>0.90' rate=87.91%
    http_req_duration{name:cart}
    ✓ 'p(95)<200' p(95)=1.52ms
    http_req_duration{name:report}
    ✓ 'p(95)<450' p(95)=391.3ms
    http_req_failed{name:pay}
    ✗ 'rate<0.08' rate=15.06%
```

- checks (availability): 87.91% (2503 out of 2847), SLO ≥ 90%: хангагдаагүй (FAIL)
- /pay error rate (reliability): 15.06%, SLO < 8%: хангагдаагүй (FAIL)
- Нийт http_req_failed: 12.08% (344 out of 2847)
- Бодит availability (хүсэлтээр) = (2847 - 344) / 2847 = 87.92%

**Error budget:** цагаар тооцвол 120 с x 10% = 12 секунд. Хүсэлтээр тооцвол 2847 check-ийн 10% буюу 284 бүтэлгүйтэл зөвшөөрөгдөх бол бодит бүтэлгүйтэл 344 байсан тул budget хэтэрсэн. Хоёр тоо зөрөх шалтгаан: сервер унасан үед хүсэлт connection refused-ээр агшин зуур буцаж /report-ийн 200-400 мс хүлээлт алга болдог, тиймээс VU бүр зогсолтын секундэд хэвийн секундээс олон хүсэлт илгээж, нэг секундийн зогсолт илүү олон хүсэлт болж тоологддог. Нэмэх нь /pay-ийн суулгасан ~5% алдаа зогсолтоос үл хамааран availability-д орсон.

**Нэг эвдрэл хоёр SLO-г зөрчих:** сервер унахад /pay-ийн хүсэлт бүр бүтэлгүйтдэг тул reliability болон availability хоёулаа зөрчигдөж болно. SLI-г тусгаарлахын тулд reliability-г зөвхөн сервер ажиллаж байх үеийн (connection амжилттай) хүсэлтийн 5xx хувиар, availability-г бүх хүсэлтийн амжилтын хувиар хэмжих хэрэгтэй.

## Зориуд FAIL (Алхам 6)

slo-test-fail.js: /report p(95)<100 (сервер 200 мс-ээс хурдан хариулдаггүй тул ямар ч машин дээр FAIL), /cart/add p(95)<50. Гаралт: results/fail.txt.

```
    checks
    ✓ 'rate>0.90' rate=98.38%
    http_req_duration{name:cart}
    ✓ 'p(95)<50' p(95)=1.31ms
    http_req_duration{name:report}
    ✗ 'p(95)<100' p(95)=390.46ms
    http_req_failed{name:pay}
    ✓ 'rate<0.08' rate=4.83%
```

k6 exit code: **99** (results/fail.txt-ийн сүүлийн мөр: exit=99). Threshold зөрчигдсөн үед k6 тэг биш код буцаадаг тул CI pipeline энэ кодоор build-ийг зогсооно. /report p(95)<100: хангагдаагүй (FAIL); /cart/add p(95)<50: хангагдсан (PASS), учир нь localhost дээр /cart/add дунджаар 1.14ms-д хариулдаг тул 50 мс-ээс хол байна.

## Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү нь босгыг бодитоор сонгох байлаа: localhost дээр /cart/add дунджаар 1.14ms-д хариулдаг тул p(95)<200 бараг юу ч шүүхгүй. Харин /report-ийн p(95)<450 босго нь 200-400 мс хиймэл хүлээлттэй ойрхон тул утга учиртай хэмжүүр болсон. Chaos туршилтад 2847 check-ийн 2503 амжилттай буюу availability 87.91% гарч, 90%-ийн SLO хангагдаагүй (FAIL). Хүсэлтээр тооцсон availability 87.92% бөгөөд /pay-ийн суулгасан ~5% алдаа үүнд багтсан тул цагаар тооцсон 12 секундийн budget-тэй шууд харьцуулагдахгүй. Зогсолтын үед хүсэлт хүлээлтгүй буцдаг тул нэг секундэд илүү олон хүсэлт бүртгэгдэж, error budget хүсэлтээр өөр хувь болж байна. Error budget (нийт check-ийн 10%) хэтэрсэн. Reliability threshold хангагдаагүй (FAIL) бөгөөд нэг эвдрэл (сервер унах) /pay-ийн SLO болон availability SLO-г зэрэг зөрчиж болдгийг харуулсан. Chaos туршилт availability SLO-г үгүйсгэв: 10 секундийн зогсолт 90%-ийн босгыг давуулсан тул босго энэ зогсолтод хэт өөдрөг байсан. Зориуд хатуу болгосон /report p(95)<100 threshold FAIL болж k6 99 гэсэн exit code буцаасан нь CI quality gate-ийн зарчим. README-ийн бүх тоо results/ доторх гаралтаас авсан.
