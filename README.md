# F.CSA313 — Лаборатори №3: Чанарын сценарио → SLO → k6 threshold

**Оюутан:** Б. Отгонсүх
**Код:** B242270021

**k6 version:**

## Тестлэх API

Node.js + Express, гурван endpoint:
- `POST /cart/add` — хурдан endpoint (сагсанд нэмэх)
- `GET /report` — удаан endpoint (200-400мс санамсаргүй хүлээлт)
- `POST /pay` — найдваргүй endpoint (хүсэлтийн ~5% нь 500 алдаа)

## Чанарын сценариоуд (6 хэсэгтэй формат)

### Сценарио 1: Performance — /cart/add хариу хугацаа

| Хэсэг | Тайлбар |
|---|---|
| Тойм | /cart/add endpoint-ийн хариу хугацааг хэвийн ачааллын үед хэмжинэ |
| Системийн төлөв | Сервер хэвийн ажиллагаатай, унаагүй |
| Орчны төлөв | Хэвийн ачаалал: 20 VU (виртуал хэрэглэгч), тогтмол ачаалал |
| Гадаад өдөөлт | 20 хэрэглэгч нэгэн зэрэг /cart/add рүү POST хүсэлт байнга илгээнэ |
| Шаардлагатай хариу | Сервер `{ ok: true, items: 1 }` гэсэн JSON хариу буцаана |
| Хэмжүүр | Хариу хугацааны p95 < 200 мс (1 минутын турш) |

### Сценарио 2: Reliability — /pay эвдрэлийн давтамж

| Хэсэг | Тайлбар |
|---|---|
| Тойм | /pay endpoint дээрх төлбөрийн хүсэлтийн бүтэлгүйтлийн давтамжийг хэмжинэ |
| Системийн төлөв | Сервер хэвийн ажиллагаатай |
| Орчны төлөв | Хэвийн ачаалал: 20 VU, 1 минутын турш |
| Гадаад өдөөлт | Хэрэглэгч төлбөр хийх зорилгоор /pay рүү POST хүсэлт илгээнэ |
| Шаардлагатай хариу | Ихэнх тохиолдолд (≥92%) амжилттай (200), заримдаа gateway timeout (500) |
| Хэмжүүр | POFOD / error rate < 8% |

### Сценарио 3: Availability — сервер унаж дахин асахад

| Хэсэг | Тайлбар |
|---|---|
| Тойм | Сервер гэнэт зогсоод дахин асахад системийн ерөнхий боломжит байдлыг хэмжинэ |
| Системийн төлөв | Ажиллаж байгаад гэнэт эвдэрч (crash), дараа нь дахин асна |
| Орчны төлөв | 10 VU, 2 минутын турш, дунд нь ойролцоогоор 10 секунд сервер зогсоно |
| Гадаад өдөөлт | Сервер process гараар зогсоож (Ctrl+C), 10 секундийн дараа дахин асаана |
| Шаардлагатай хариу | Систем аль болох хурдан сэргэж, зогсолтоос гадуур хүсэлтүүд амжилттай хариу авна |
| Хэмжүүр | Availability (амжилттай хүсэлтийн хувь) ≥ 90%, сэргэх хугацаа (recovery time) ойролцоогоор 10 секунд |

## SLO (Service Level Objective)

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 200 мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, 10с зогсолт орсон |

**Босго сонгосон үндэслэл:** /pay endpoint дээр серверт зориудаар ~5% алдаа суулгасан тул 8% гэдэг нь энгийн хэлбэлзлийг тэвчих боловч бодит асуудлыг илрүүлэх боломжтой, бодит дээр суурилсан босго юм. Performance-ийн хувьд 200мс нь хэрэглэгчийн хувьд "хурдан" гэж мэдрэгдэх ерөнхий стандарт хугацаа.

**Error budget тооцоо (цагаар):** Availability SLO маань 2 минутын цонхонд ≥90% байхыг шаардаж байгаа тул зөвшөөрөгдөх "эвдрэх хугацаа" нь: 120 сек × (1 − 0.90) = **12 секунд**. Өөрөөр хэлбэл, 2 минутын турш нийт 12 секундээс илүүгүй хугацаанд систем боломжгүй байж болно гэсэн үг.

## k6 Threshold-ууд (slo-test.js)

| Threshold | Тайлбар |
|---|---|
| `http_req_duration{name:cart}`: p(95)<200 | Performance SLO |
| `http_req_failed{name:pay}`: rate<0.08 | Reliability SLO |
| `checks`: rate>0.90 | Availability SLO |
| `http_req_duration{name:report}`: p(95)<450 | Нэмэлт (4-р) сценарио — /report-ийн латенси |

PASS гаралт: `results/pass.txt` (бүх 4 threshold ✓)

**Ажиглалт:** localhost дээр /cart/add ердөө ~3.7мс-д хариулдаг тул p(95)<200 threshold бодит дээр маш сул (бараг юу ч шүүхгүй) байна. Харин /report-ийн хувьд 200-400мс хиймэл хүлээлт кодонд шууд суулгасан тул p(95)<450 threshold бодит утгатай ойрхон, утга учиртай хэмжүүр болж байна.
